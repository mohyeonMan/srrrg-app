# srrrg-k3s 코드 컨벤션

이 문서는 기능과 관계없이 적용할 공통 규칙을 정한다. 인증, 링크, 프로젝트처럼 기능에만 해당하는 정책과 API 계약은 해당 기능 문서에서 정한다. 기존 `srrrg`의 구현은 참고 자료이며 새 저장소의 현재 코드와 이 문서를 우선한다.

## 1. 형식과 이름

- UTF-8과 파일 끝 개행을 사용한다. 줄바꿈과 들여쓰기는 `.editorconfig`를 따른다.
- Java와 Gradle은 탭 들여쓰기, YAML은 공백 두 칸, SQL은 공백 네 칸을 사용한다.
- Java 타입은 `PascalCase`, 메서드와 변수는 `camelCase`, 상수와 환경 변수는 `UPPER_SNAKE_CASE`, DB 식별자는 `snake_case`를 사용한다.
- 이름은 역할과 동작을 드러내고, 같은 개념에는 같은 용어를 사용한다. `data`, `process`, `handle`처럼 뜻이 넓은 이름은 구체적인 이름으로 바꾼다.
- 와일드카드 import를 사용하지 않는다. 요청과 무관한 파일 전체 포맷이나 import 정리를 섞지 않는다.
- 독립적인 최상위 타입은 파일을 따로 둔다. 한 클래스에서만 쓰는 구현 세부사항은 내부 `class`, `enum`, `record`로 둘 수 있다.

## 2. 구조와 책임

- 패키지는 `link.srrrg.<기능>.<역할>`을 기본으로 한다. 실제 코드가 생길 때 필요한 역할 패키지만 만든다.
- HTTP 계약은 Controller, 유스케이스와 트랜잭션은 Service, 저장은 Repository가 담당한다. 업무 요청의 Controller는 Repository를 직접 호출하지 않는다.
- 구현체 하나만을 위한 인터페이스, 단순 위임 계층, 미래를 가정한 설정과 `common` 수납 공간을 만들지 않는다.
- 한 클래스와 메서드에는 같은 이유로 바뀌는 책임을 모은다. 파일 길이만을 이유로 나누지 않는다.
- 같은 업무 규칙을 여러 곳에 복사하지 않는다. 코드 모양만 비슷하고 변경 이유가 다른 부분은 억지로 공통화하지 않는다.
- 엔티티를 API 응답으로 직접 반환하지 않는다. 단순한 요청·응답과 불변 값은 `record`를 우선한다.

### 메서드와 제어 흐름

- 메서드 이름과 인자만으로 주요 동작을 이해할 수 있게 한다. 서로 다른 단계를 한 메서드에 섞어 읽기 어려워지면 책임별로 나눈다.
- 예외 조건은 초기에 처리하고 정상 흐름을 따라 읽기 쉽게 둔다. 깊은 중첩과 복잡한 조건식은 의미 있는 이름이나 작은 메서드로 풀어낸다.
- 메서드 길이와 클래스 크기에 일률적인 숫자 제한을 두지 않는다. 분리 기준은 책임과 가독성이다.

## 3. Spring과 Lombok

- Spring이 제공하는 보안, 검증, 설정 바인딩, 예외 처리 기능을 먼저 검토한다. 같은 일을 하는 자체 필터나 어노테이션을 관성적으로 만들지 않는다.
- 의존성은 생성자로 주입한다. 필요한 `final` 필드의 생성자는 Lombok `@RequiredArgsConstructor`를 사용할 수 있으며 필드 주입은 사용하지 않는다.
- JPA 엔티티에는 필요한 접근자와 보호된 기본 생성자만 Lombok으로 만든다. 상태를 제한 없이 바꿀 수 있는 클래스 단위 `@Setter`나 `@Data`를 붙이지 않는다.
- 재할당할 필요가 없는 필드와 지역 변수는 `final`을 사용한다. 변경 가능한 상태가 필요하면 상태를 바꾸는 메서드에서 유효한 전이만 허용한다.
- `@Transactional`, `@Valid`, `@ConfigurationProperties`처럼 경계와 계약을 나타내는 어노테이션을 해당 책임을 가진 곳에 사용한다. 의미가 중복되는 어노테이션은 추가하지 않는다.
- 설정값은 관련 항목을 묶어 타입으로 바인딩하고, 비밀값은 환경 변수나 외부 설정에서 받는다.

## 4. 데이터와 동시성

- DB 스키마는 Flyway가 소유한다. 적용한 migration은 수정하지 않고 새 버전을 추가한다. JPA를 사용하면 `ddl-auto=validate`, `open-in-view=false`로 둔다.
- 절대 시각은 `Instant`를 우선한다. 같은 작업에서 한 기준 시각이 필요하면 한 번 읽거나 `Clock`을 주입한다.
- 외부 HTTP 응답을 기다리는 동안 DB 트랜잭션을 열어 두지 않는다. 조회 후 저장의 경쟁 조건은 DB 제약이나 원자적 연산으로 막는다.
- 여러 파드 사이에서 공유해야 하는 상태에 JVM 메모리나 lock을 사용하지 않는다. 스케줄 작업은 파드마다 실행될 수 있음을 전제로 한다.

## 5. API, 보안, 오류

- JSON 필드는 `camelCase`, 날짜와 시각은 ISO 8601을 사용한다. 경로·상태 코드·오류 형식·인증 정책은 기능 구현 전에 계약으로 정한다.
- HTTP 요청과 외부 시스템 응답은 경계에서 검증한다. 필드 제약은 가능한 경우 Spring Bean Validation으로 표현하고, 여러 값에 걸친 업무 조건은 담당 계층에서 확인한다.
- 예상 가능한 업무 실패와 시스템 장애를 구분하고, 호출자가 알 수 있는 결과로 처리한다. 예외를 삼키거나 광범위하게 잡아 정상 결과로 바꾸지 않으며 보안 실패를 임의로 허용하지 않는다.
- 비밀번호, 토큰, 쿠키, 전체 인증 헤더와 민감한 요청 값은 코드나 로그에 남기지 않는다. 원문 저장이 필요한지 먼저 검토하고, 불필요하면 해시나 최소 식별자만 저장한다.

## 6. 주석과 검증

- 한국어 주석은 코드만으로 드러나지 않는 정책, 순서, 신뢰 경계와 실패 결과의 이유를 설명한다. 이름이나 문법을 반복하는 주석은 쓰지 않는다.
- 변경한 동작에 가장 가까운 테스트부터 실행한다. 정책은 단위 테스트, HTTP·DB 경계는 필요한 통합 테스트로 검증한다.
- 테스트는 내부 구현을 그대로 따라 쓰지 않고 외부에서 관찰되는 결과를 확인한다. 실행하지 못한 검증은 이유와 함께 보고한다.
- 정상 흐름뿐 아니라 중요한 실패와 경계 조건을 검증한다. 구현 세부사항에 묶인 테스트보다 정책이 바뀌면 함께 바뀌어야 할 테스트를 남긴다.

## 7. 커밋

### 메시지 형식

~~~text
타입 : 한글 요약
- 한글 상세 내용 1
- 한글 상세 내용 2
~~~

상세 설명이 필요 없는 단순 변경은 제목만 작성할 수 있다.

| 타입 | 용도 |
|---|---|
| feat | 기능 추가 |
| fix | 버그 수정 |
| refactor | 외부 동작 변경 없는 구조 개선 |
| test | 테스트 추가·수정 |
| docs | 문서 추가·수정 |
| chore | 일반 설정과 기타 작업 |
| build | Gradle, Docker 등 빌드 변경 |
| ci | CI 변경 |
| perf | 성능 개선 |

- 타입과 요약 사이에는 “ : ”를 사용한다.
- 요약은 한글로 간결하게 작성하고 마침표를 붙이지 않는다.
- 본문에는 무엇을 왜 변경했는지 구체적으로 작성한다.
- 본문의 상세 항목은 핵심 변경만 2~3줄로 간결하게 작성한다.
- 한 커밋에는 하나의 논리적인 변경만 포함한다.
- “수정”, “작업”처럼 변경 내용을 알 수 없는 요약을 사용하지 않는다.
- 제목, 본문, 꼬리말에는 실제 변경 내용만 기록한다.
- AI 제품·모델·도구 이름, 생성·지원 표기, 공동 작성자, 이모지, 자동 서명과 관련 링크를 넣지 않는다.

Git stage, commit, push와 이력 변경은 사용자가 명시적으로 요청했을 때만 수행한다.
